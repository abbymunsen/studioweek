# StudioWeek

One person's class schedules from many studio booking platforms, consolidated into a single
filterable board. No server: a scheduled GitHub Action fetches feeds, normalizes them, and commits
JSON; the frontend is a static site that filters client-side; starred classes emit an `.ics`
calendar-subscription feed.

**Everything in this repo is synthetic.** The eight studios, their teachers, and their schedules are
generated by two demo adapters. Real platform adapters — actual endpoints, headers, parsing — live in
a private repo *by design* (they encode other people's undocumented APIs and one person's location
data) and plug into this engine through the adapter interface below.

## Architecture

```
studio configs (TOML)          adapters (one per booking platform)
   one per studio      ──────►   demo-api / demo-scrape here;
        │                        real ones private, loaded via --adapters
        │                              │  RawClassInstance[]
        ▼                              ▼
  ┌────────────────────────────────────────────────────┐
  │ fetch CLI: normalize → America/New_York wall time  │
  │   → derive recurring key → tag cascade → merge     │
  └────────────────────────────────────────────────────┘
        │                    │                  │
        ▼                    ▼                  ▼
  dataset.json         summary.json       studioweek.ics
  (committed)      (untagged names,     (starred keys ×
        │           dropped classes,      instances)
        ▼           adapter health)
  static frontend: week board / day board / directory,
  all filtering client-side over the full dataset
```

The cron runs every few hours in the private repo, which checks out this repo pinned to a tag and
runs its CLI against private configs. A weekly cron *here* regenerates the demo dataset for the
current week, so the public deployment is the real pipeline running end to end on fake studios.

## The interesting decisions

**Class instances are the only stored records.** Feeds provide instances; recurring identity is a
*derived* key — `studio | weekday | wall-time | slug(name)` — computed by one function and used
wherever an annotation (star, tag override, note) needs to stick across weeks. No class-type or
recurrence entities. The slug normalizer aggressively strips substitution chatter ("w/ Sam covering",
"(sub: Noa)") so annotations survive the renames studios actually make. Keys use New-York *wall time*,
so DST transitions don't move them.

**Tags are flat; authoring is a cascade.** Studio defaults → per-studio name-pattern rules
(add/remove/exclude) → per-key overrides. `exclude` drops a class at ingest and the run summary says
what was dropped by which rule; borderline classes get a `fringe` tag (hidden by default, one toggle
to show). Classes no rule matched land in a visible **untagged** bucket and the summary lists their
names — taxonomy upkeep is a glance, not a chore.

**Failure policy: red means act.** A failed adapter's studio keeps its previous data (badged stale in
the UI); a single failed run is a warning in the job summary; the Action only goes red when a studio's
freshest data is >24h old. One flaky fetch never paints the week red, and silent staleness can't happen.

**Times are strings on purpose.** Everything is normalized to `America/New_York` with explicit
offsets at ingest — the only place timezone math exists. The frontend never constructs a `Date` from
a timestamp; display is string slicing, correct in any viewer timezone.

## Run it

```bash
npm ci
npm run demo:fetch   # synthetic platforms → demo/data/dataset.json (+ run summary)
npm run demo:ics     # starred keys → demo/data/studioweek.ics
npm test
npm run web:dev      # board at localhost:5173, over the demo dataset
```

## Adding a platform, adding a studio

A platform is one module implementing `PlatformAdapter`
([src/adapters/types.ts](src/adapters/types.ts)): translate one studio's feed into
`RawClassInstance[]` for a date window. Adapters never touch tags, keys, or timezones — so a new
studio on a known platform is a **config file, not code**: id, color, address, pricing, teachers,
tag rules ([demo/studios/](demo/studios/) has eight examples). `validate` checks every config in CI.

The engine loads external adapters from a directory (`--adapters <dir>`), which is how the private
repo plugs in real platforms without this repo ever naming them.

## Layout

```
src/core/       schema, recurring-key, tags, normalize, ics, summary
src/adapters/   the adapter interface + registry + two synthetic platforms
src/cli/        fetch, build-ics, validate, geocode
web/            vanilla TS + Vite frontend (no framework — 8 KB gzipped)
demo/           synthetic studio configs, annotations, committed demo dataset
worker/         optional Cloudflare Worker for cross-device star sync
docs/design/    the design prototypes the frontend implements
```

Stack: TypeScript on Node 22, zod, luxon, smol-toml, Vite, Vitest. Chosen to still build in three
years; the frontend has zero runtime dependencies.
